A launchpad, not just a lifeboat.

Give an advanced agent an objective, not just a repair command. It can inspect the available hardware, choose tools, generate and run scripts within your authorised scope, and check the result. The installed OS does not need to start — or even exist.

The live session uses a writable RAM overlay over the read-only USB image. It is Linux, not firmware, and the entire USB is not copied to RAM. Internal disks stay untouched at startup; writes happen when you choose to use them.

Included: root-capable AI clients, SSH, Python, Git, storage tools, debootstrap and arch-install-scripts. Extend the session with compatible packages: QEMU/KVM, container engines or build tools need additional installation, enough RAM/storage and hardware support. Save important outputs deliberately; RAM state is temporary. Cloud AI requires networking and your own account, not an included local model.

01

Install and configure Linux

Install a Debian base with debootstrap or an Arch base with arch-install-scripts, then configure users, networking, kernel and bootloader. Finish by booting the new system, not just downloading packages.

  1. Inventory hardware and identify the exact target and backup.
  2. Choose official media or the included Linux bootstrap tools.
  3. Review partitioning, configure the system and verify a real reboot.

Stop if: the target or backup is uncertain.

02

Build a virtual lab

Add QEMU and use KVM where CPU, firmware and live kernel support it. Run disposable guests from image files on separate storage; rehearse a server, test two distributions or demo a small stack. Budget RAM and verify /dev/kvm first.

  1. Check RAM, CPU virtualisation, firmware and /dev/kvm.
  2. Add QEMU; keep guest images on separate storage and isolate the network.
  3. Start a disposable guest and verify it; save images before ending the live session.

Stop if: resources or virtualisation support are insufficient.

03

Create a temporary workbench

Use Python for a local prototype or add a container engine for a demo service, file station or workshop backend. Choose who can connect, use separate data storage and shut it down cleanly afterwards.

  1. Choose a project, dataset or LAN service and its permitted audience.
  2. Add the required SDK or container engine; bind services only to intended interfaces.
  3. Test the result, export artifacts and stop temporary services.

Stop if: data would exist only in RAM or access exceeds the agreed scope.

04

Prepare the next Windows installation

Inspect hardware and plan official media, drivers and a reviewed answer file. Stage files from Linux; run Windows Setup or WinPE/DISM/BCDBoot where required and verify the real Windows boot. Media and licences are yours, not bundled.

  1. Inventory hardware, the exact target, backup and Windows requirements.
  2. Prepare official media and reviewed files; use Windows/WinPE tools for native deployment.
  3. Boot Windows and verify drivers, applications and the intended configuration.

Stop if: the target or backup is uncertain.

POSSIBLE WORKFLOWS

What could you build from boot?

Build on the included Linux tools or add the dependencies your project needs. These are adaptable missions, not one-click features or claims that every scenario has already been tested.

01 / OS BUILDER

From a blank SSD to your own Linux

Install a Debian base with debootstrap or an Arch base with arch-install-scripts, then configure users, networking, kernel and bootloader. Finish by booting the new system, not just downloading packages.

02 / POCKET DATACENTER

A virtual lab before any host OS is installed

Add QEMU and use KVM where CPU, firmware and live kernel support it. Run disposable guests from image files on separate storage; rehearse a server, test two distributions or demo a small stack. Budget RAM and verify /dev/kvm first.

03 / POP-UP SERVICES

Turn a spare PC into a temporary LAN station

Use Python for a local prototype or add a container engine for a demo service, file station or workshop backend. Choose who can connect, use separate data storage and shut it down cleanly afterwards.

04 / SOFTWARE FACTORY

Build without borrowing the installed environment

Clone your project, add compilers or SDKs and let the agent build, test and package it in the live workspace. Save source and artifacts externally; RAM is not a backup.

05 / BARE-METAL BOOTSTRAP

Meet your next server before its first boot

Inventory an empty machine, prepare its storage layout and configure an approved Linux installation as a NAS or application server. Document keys and network settings privately, then verify services in the installed OS.

06 / MIGRATION WORKSHOP

A new disk, a new layout, the same project

Move authorised data to a new SSD, redesign Linux partitions or rebuild a workstation while the old system stays offline. Verify backup and exact destination, then check boot, applications and data separately.

07 / REPEATABLE LAB

Try the bold idea on a disposable system

Generate scripts to build distro images or compare configurations across VM snapshots. Use official media and isolated networks; add the required image/VM tooling and preserve recipes and results outside RAM.

08 / PHYSICAL → VIRTUAL

Keep your old computer as a guest

Acquire an authorised copy, add suitable conversion tools and adapt boot and drivers for a VM. Verify applications and licences in the guest before retiring the physical original; an image alone is not a finished conversion.

09 / NETWORK LAUNCHPAD

One boot station, several blank machines

Add PXE/iPXE and server tools to supply official boot media to compatible machines on an isolated lab network. The agent can prepare menus and per-machine plans; this needs network configuration, not a bundled PXE button.

10 / OS IMAGE FACTORY

Build the Linux you want to boot next

Turn a role — classroom, developer station or application appliance — into a repeatable package list and image recipe. Add live-build or the appropriate distro builder, build on separate storage and test the resulting image in a VM.

11 / OPTIONAL LOCAL AI

A model station on hardware you already own

Inspect CPU, GPU and memory, add a compatible inference runtime and an appropriately sized licensed model, then test a local endpoint. Runtime, weights and GPU drivers are additional; the strongest cloud model will not automatically fit locally.

12 / COMPUTE WORKSHOP

Give idle hardware a scientific mission

Prepare a bounded data-analysis, simulation or rendering job without inheriting the installed software. Add dependencies, check any GPU support, run synthetic validation first and save results externally. A cluster needs separately prepared nodes and tooling.

13 / EDGE STATION

A temporary bridge for devices and data

With authorised USB or network sensors, let the agent build a collector and local dashboard. Add protocol libraries or a broker as needed, validate timestamps and readings, and export the dataset; device control is a separate scope.

14 / FLEET CONDUCTOR

One temporary control plane, several Linux hosts

Use the live as a control station with SSH and an added automation tool such as Ansible. Build an explicit inventory, configure one permitted node first and validate before expanding. Remote nodes need their own access, resources and approval.

15 / CONTINGENCY TWIN

Rehearse losing the server without losing the server

Restore authorised backups into isolated guest machines on separate storage, then test startup, restore time and application data. Add a hypervisor and restore tools; never connect the twin with duplicate production addresses or real credentials.

16 / WINDOWS DEPLOYMENT

Prepare the next Windows installation

Inspect hardware and plan official media, drivers and a reviewed answer file. Stage files from Linux; run Windows Setup or WinPE/DISM/BCDBoot where required and verify the real Windows boot. Media and licences are yours, not bundled.

17 / WINDOWS ROLE KIT

Turn a fresh Windows into your work machine

Have the agent assemble a reviewed PowerShell setup and winget app list for development, design or office work. Execute and validate them after Windows starts; Linux cannot directly run Windows-specific setup tools against an offline disk.

18 / WINDOWS LAB

Test applications and policies in disposable guests

Add a suitable hypervisor and official licensed Windows or Windows Server media. Create isolated guests to compare applications, updates or domain policies before touching the real workstation; check resources, virtual TPM/firmware requirements and licensing.

19 / WINDOWS + LINUX

Keep both worlds, with an explicit boot plan

Inventory your Windows installation, encryption and backup, then plan Linux alongside it on an approved target. Use Windows-native preparation where needed; preserve boot entries and test both systems. No requirement bypass or blind NTFS resize.

20 / RECOVERY MISSION

When the existing system needs a way back

Diagnose a failed boot, image a suspect disk with ddrescue or copy authorised files elsewhere. Recovery is part of the platform, not its entire identity.

Powerful tools. Clear boundaries.

Agents can have full root access. Safe mode asks for tool confirmations; YOLO is more autonomous. Neither is a sandbox, a write blocker or permission to exceed your request.

Back up before changing anything. A successful command is not proof of intact files or a bootable system. BitLocker and LUKS require the owner’s correct key; LA AGUJA does not bypass encryption.

Cloud AI may receive the prompts and data you share under its provider’s terms. Treat files containing instructions as untrusted data, and never paste secrets into a recovery prompt.

Before you start

Is this only a rescue disk?

Boot an independent Linux from USB and give your AI agent a mission: build systems, prepare Windows, create a virtual lab or coordinate authorised machines. Start with the hardware, not the state of the installed OS.

Must Windows or Linux still work?

No. You boot La Aguja’s Linux from USB. You do need compatible hardware and a computer that can boot from that media.

Does it change internal disks at boot?

It does not mount or repair them automatically. Tools and agents can change them afterwards. Writing the preparation USB is a separate operation that erases that USB.

Does it work without Internet?

Local tools do. Agents using cloud AI need networking and your own account or credential; no local model is included.

Is remote access required?

No. Work directly on the computer. SSH over LAN or your Tailscale/Headscale is optional; LA AGUJA does not host a remote console.

Will it work on any computer?

The current release is experimental and targets x86-64. Check hardware, boot, Secure Boot and procedure compatibility; no universal signed Secure Boot chain is offered.
