# Flash Imager for AI agents

Create the requested **file image**, not a physical disk write. Work through the harness's available file and shell tools; the procedure does not depend on a model, provider, MCP server or UI. Reply in the user's language.

Requires Node.js 22+, file/shell access and space for both images. Network is needed for downloads, not local preparation. No root or Electron is needed.

1. Locate this skill directory and run `node <skill-dir>/scripts/imager.cjs doctor`. The release ZIP includes the engine; in a repository checkout run `npm ci --prefix desktop` if its dependency is missing. For discovery paths and manual loading in other harnesses read [references/harnesses.md](references/harnesses.md). Without execution/file access, provide the configuration plan, not a claim of a created image.
2. Translate the request into supported settings: hostname, locale/keyboard, DHCP or static Ethernet, optional Wi-Fi, SSH public key/password, and optional provider or Tailscale/Headscale configuration. Read [references/interface.md](references/interface.md) for the input contract; run `locales` for valid language/keyboard values. Use the caller's authorised settings and ask only for essentials that are missing, such as an SSH public key. Leave optional authentication off unless requested. A preparer harness and the agents inside the live image are different: the image currently supports Codex, Claude, Antigravity and OpenCode profiles, not arbitrary additional harness installations.
3. Obtain the official base `.img` with `catalog` and `download`, which verify the pinned Ed25519 catalogue and image/part hashes. An existing decompressed `.img` can be checked with `inspect` against a trusted expected SHA-256. A calculated digest alone does not prove official origin; do not mark an offline/local image as signature-verified. Do not modify the factory image or claim this profile workflow rebuilds the Linux distribution, installs additional packages, creates a Windows installer or produces a customised ISO.
4. Create the private request through a secure file tool or pipe, never by putting secrets into command arguments, shell history, chat, logs or a committed template. Use [assets/request.example.json](assets/request.example.json) as a credential-free skeleton; replace its paths, hash and SSH public key. Keep request files private (0600 on POSIX; restricted user ACLs on Windows). Use encrypted protection for passwords, API keys, imported sessions or tailnet keys; obtain the unlock phrase through the harness's secure input/secret mechanism, outside chat. A public-key-only profile can be plain. If secure secret handling is unavailable, use public-key-only preparation or let the user enter secrets in the desktop Imager. Import only explicitly requested compatible native provider sessions via `import_providers`; never copy an entire home directory, browser/keychain, hooks or history.
5. Feed the JSON request to `node <skill-dir>/scripts/imager.cjs prepare` through stdin, using the harness's process API or the shell-specific pipe in the interface reference. Require exit code zero and final JSON with `ok`, `profile_verified`, `source_unchanged` and `device_written:false`. Return the output path, SHA-256, bytes, profile protection and any remaining boot verification. Do not expose the capsule. Keep the private image and unlock phrase out of public releases. Remove only task-owned secret request files using the environment's approved secure handling.
6. **Stop at the file unless USB writing was explicitly requested.** Before any later physical write, identify the exact model, capacity, path and serial, establish a recoverable backup and obtain confirmation covering that device's erasure. Use the desktop Imager or the repository's existing guarded writer, not an improvised `dd`. A successful image build is not proof of USB readback, BIOS/UEFI boot, login or network connectivity: report these separately and test them only within the authorised scope.
