# Manual disk recovery keys and agent context

The `disk_recovery` field of a private prepare request accepts BitLocker numerical recovery passwords (48 digits, eight six-digit groups) and existing LUKS passphrases/recovery keys. Supply type, a nonempty equipment/disk label, optional protector ID or LUKS UUID, and the exact key. LUKS spaces/Unicode are preserved. An ID is not a key, and format validation does not prove the selected target opens. Binary keyfiles and other encryption formats are not supported by this interface.

The preparer can run on a different computer/OS from the target. Do not harvest local BitLocker, search whole profiles, enrol accounts or operate physical disks to populate this field. Use only keys explicitly supplied or selected by the owner through secure input. Keep JSON on private stdin/files; never argv, console output, logs, chat, screenshots or committed examples. Recovery entries require encrypted protection unless `allow_plain_secrets:true` was explicitly authorised.

The same production engine as the desktop writes supplemental `aguja-recovery.json`, a standalone `aguja-recovery.py`, usage notes and an empty legacy BitLocker stub. The boot profile schema stays compatible. Each file is read back before the new output is published; encrypted key bytes never appear in the plaintext CFG profile. The same image unlock phrase protects both capsules. Skill 1.0.4 and engine 0.9.15 are separate version identities; run `doctor` and `catalog`.

On Rescue 0.9.15+, agents start with `aguja secrets --json` and `sudo aguja recovery status --json`, and read `/usr/share/aguja/SECRETS.md` plus `/usr/share/aguja/skills/disk-recovery/SKILL.md`. Plain keys load into private RAM at boot; `aguja profile unlock` opens a matching encrypted recovery capsule into `/run/aguja-recovery/keys.json` (root, 0600/0700, RAM only). `sudo aguja recovery unlock` is the independent interactive fallback. `list --json` returns labels/IDs, not keys. `open INDEX EXACT-DEVICE` uses private input to cryptsetup and defaults to a read-only mapping, without mounting/repairing. A reboot relocks the capsules.

On older compatible Rescue images (including 0.9.11), the standalone helper supplied in CFG remains usable through `sudo python3 /config/aguja-recovery.py list|export|open`; it asks for the password separately and does not automatically integrate with boot or agent launchers. Do not promise new native commands on old images. A file-image preparation does not upgrade an already booted live, unlock a real disk or authorise permanent decryption/writes.
